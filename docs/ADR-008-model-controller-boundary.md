# ADR-008: The model-controller boundary (v0.6.0, M6)

Status: accepted, 2026-10-16. Implemented and verified with fixtures and mocked transport only; no live model call has been made.

## Context

M5c closed the offline search-tuning cycle. M6 adds inhabitants whose decisions come from a language model, without giving up the properties every earlier milestone relied on: an authoritative deterministic engine, hash-chained tick records, replay without controllers, and honest attribution. A network call is slow, can fail ambiguously, may cost money, and cannot be repeated safely. None of that may leak into world state.

## Decisions

1. **Two phases per tick.** Phase A (outside the write transaction) schedules, reserves budget, dispatches and persists responses in short ledger transactions. Phase B (inside `BEGIN IMMEDIATE`) checks that the world state hash is unchanged, runs a pure controller that turns prepared responses into one `Action` per model agent (or a labelled fallback), lets the engine validate and apply, and marks ledger rows `consumed` in the same transaction as the tick. No I/O happens while the write lock is held.
2. **One wire protocol: Ollama `/api/chat`**, non-streamed. Structured outputs (a JSON Schema in `format`) is a declared per-profile capability; without it the adapter asks for `format: "json"` and relies on the strict parser. `thinking` and other reasoning fields are discarded and never stored. References: <https://docs.ollama.com/api/chat>, <https://docs.ollama.com/capabilities/structured-outputs> (checked 2026-10-16; Ollama's cloud models are documented without structured-output support). Ollama offers no idempotency key and no request-status lookup, which drives decision 5.
3. **Strict output contract.** One JSON object with `kind`, `params`, optional `explanation` (≤ 200 chars) and `standing`. Unknown kinds, wrong parameter sets, extra fields (including any agent identity), non-finite numbers and oversized strings are parse errors. At most one repair request, then an explicit fallback. A well-formed but illegal action is an ordinary rejected world action.
4. **Prompts are built only from trusted parts**: versioned instructions, the public schema, the existing restricted observation (as an escaped data block), and bounded memory. Truncation is deterministic and recorded. Untrusted text cannot forge the data-block delimiter.
5. **A durable ledger with leases; never blindly resend.** Lifecycle `reserved → dispatching → completed → consumed`, with `cancelled-before-dispatch`, `failed-not-delivered`, `failed-delivered`, `outcome-unknown`, `expired-unconsumed` and `blocked`. A crash before dispatch cancels the row (no usage) and the decision is retried once. A crash after possible dispatch leaves the row `dispatching`; while its lease is valid other workers get `DecisionInFlight`; afterwards it becomes `outcome-unknown`, keeps its reservation, and is never sent again. A completed but unconsumed response is reused on restart. The `decision_id` is unique, so competing workers cannot both own one decision.
6. **Stable decision identity**: run, agent, committed tick, role and attempt, observation hash, prompt hash, prompt/schema/parser/adapter versions and a config hash (adapter settings that determine request content, excluding the endpoint address). It contains no secrets.
7. **Budgets reserve before dispatch.** Requests (including repairs), input and output tokens, controller time and optional integer micro-unit cost, per run and per agent, plus concurrency. Committed, pending, uncertain and historical buckets are kept apart; uncertain usage keeps its full reservation. A paid profile without prices and cost ceilings is invalid. There is no unlimited mode.
8. **Event-driven scheduling.** A model is consulted on its first decision, after a rejection, on a new message, when a standing intent ends, or at the refresh interval, never more often than `min_interval` ticks and at most `max_calls_per_tick` agents per tick. Between deliberations an agent either executes its standing model choice (`model-intent-execution`) or the offline policy acts (`offline-policy`). Every decision says which.
9. **Three replay modes.** State replay applies deltas and never calls anything. Decision re-execution rebuilds observations and prompts from replayed state and checks hashes, receipts and actions against the ledger. Recorded continuation (`mode: recorded`) reuses a source run's responses in a fork and stops on the first mismatch (or, if configured, falls back explicitly). Recorded usage is historical and is not charged again.
10. **Live calls are off by construction.** A live profile needs `live_authorized: true` and the environment variable `GENESIS_LIVE_MODEL_CALLS=1`; the API can only create fixture-backed runs; `HttpTransport` can be restricted to loopback; profiles reject credential-bearing URLs; no headers are stored; credential-like text blocks dispatch and is scrubbed from views.

## Consequences

- Runs without a model profile are unchanged (tested against v0.5.2 behaviour and copy-on-write equivalence).
- Fixture and mock-HTTP runs exercise the whole path, including real HTTP serialization over loopback, without credentials. They are scripted and say nothing about model competence.
- An `outcome-unknown` request needs an operator decision; the agent waits in labelled fallback until then. This is deliberate: guessing would risk double charging or a silently duplicated decision.
- Prompt bytes are used as the input-token reservation (an over-estimate for typical tokenizers). Reported usage replaces it when the provider returns counts; otherwise the reservation is charged.
- Not built: streaming, tool calls, other provider protocols, multi-turn agent memory beyond the observation, money accounting for any real provider (no prices have been chosen).
